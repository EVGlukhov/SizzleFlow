# План проекта SizzleFlow

## 1. Цель проекта
Цель проекта — создать учебную event-driven систему для обработки ресторанных 
заказов и на ее примере последовательно изучить возможности Apache Kafka. 
Проект должен показать, как создавать topics и partitions, выбирать ключи 
сообщений, работать с producers, consumers и consumer groups, обрабатывать сбои, 
повторы и дубликаты, управлять схемами событий и надежно связывать Kafka 
с базой данных. Функции системы будем добавлять поэтапно, чтобы каждую 
возможность Kafka можно было изучить и проверить на практике.

## 2. Каналы заказов
Заказы поступают из двух каналов: из зала ресторана, где их 
оформляет сотрудник, и онлайн — через сайт или приложение. 
Оба канала используют общий процесс обработки заказа. 
Отдельно указываются источник заказа и способ 
его получения: за столом, самовывоз или доставка. 
После подтверждения оплаты заказ передается на кухню независимо от канала.

## 3. Жизненный цикл заказа
После оформления заказ ожидает оплаты. Только после подтверждения оплаты 
он передается на кухню: `AWAITING_PAYMENT → PAID → PREPARING → READY → COMPLETED`. 
Для заказа в зале `COMPLETED` означает, что блюдо подано; для 
интернет-заказа — что его выдали или доставили. 
Отмененный или неоплаченный заказ на кухню не передается.

## 4. Архитектура и сервисы
Логические области системы: Order, Payment, Kitchen, Delivery, Notification и
Accounting. На первом этапе они реализуются как модули одного NestJS-приложения;
возможность разделить их на отдельные сервисы останется отдельным архитектурным
решением и учебным этапом.

Frontend должен показывать меню, корзину, оформление заказа и его статус,
взаимодействуя с NestJS через HTTP API. В перспективе планируется написать
небольшой собственный JavaScript-фреймворк на основе Custom Elements. Эта работа
отложена до реализации основного backend-сценария.

## 5. События Kafka
Kafka передает события между компонентами. Например,
событие `PaymentConfirmed` передается кухонному consumer-у, который создает
заявку на приготовление. Ключом сообщения служит `orderId`, чтобы события
одного заказа обрабатывались последовательно. Сейчас используется topic
`sf.order-events` с тремя partitions и consumer group `sf-kitchen`.
Список событий и их форматы будут уточняться по мере реализации.

## 6. Данные и надежность
PostgreSQL хранит заказы, их текущие статусы и необходимые детали заказа. 
Kafka используется для передачи событий, а не как замена базе данных. 
Нужно предусмотреть надежную публикацию событий, повторную обработку 
при сбоях и защиту от повторного выполнения одного события.

## 7. Этапы реализации
Реализовать заказ и его статусы, затем API и сохранение заказа. После этого
добавить тестовое подтверждение оплаты и передачу события в Kafka, кухонную
обработку и тесты. Доставку, учет и уведомления подключать следующими этапами.

На первом этапе оплату можно подтверждать тестовым способом, чтобы сосредоточиться
на потоке событий Kafka. После завершения основного backend-сценария добавить
frontend и подключить его к API.

## 8. Текущий статус

### Сделано
- Локальный Docker Compose-стек с Kafka в KRaft-режиме, Kafka UI, PostgreSQL и NestJS API.
- Topic `sf.order-events` с тремя partitions; сообщения маршрутизируются по ключу `orderId`.
- NestJS producer и consumer group `sf-kitchen`; consumer использует ручной commit Kafka offsets.
- Prisma 7 подключен к PostgreSQL. Есть модели `ProcessedEvent` и `KitchenTicket`.
- API присваивает новым событиям `eventId`. Для старых сообщений без ID используется стабильный ключ из topic, partition и offset.
- Consumer одной транзакцией записывает обработанное событие и создает не более одной кухонной заявки на заказ при `PaymentConfirmed`. Kafka offset подтверждается после транзакции.
- Сборка API и ручная проверка повтора `PaymentConfirmed` прошли: созданы одна запись `ProcessedEvent` и одна `KitchenTicket`.

### Осталось для первого сквозного сценария
1. Добавить модель заказа с позициями, источником заказа и способом получения.
2. Реализовать API создания заказа и хранить его состояние, начиная с `AWAITING_PAYMENT`.
3. Добавить тестовое подтверждение оплаты для существующего неоплаченного заказа. Сейчас тестовый `POST /events` публикует произвольное событие и не проверяет наличие заказа или факт оплаты.
4. Связать кухонную заявку с составом заказа и добавить получение заявок и переходы статусов, например `QUEUED → PREPARING → READY`.
5. Добавить автоматические тесты ключевых сценариев: неоплаченный заказ не попадает на кухню, повтор события не создает повторный эффект, ошибка БД не приводит к commit Kafka offset.

### Следующие этапы
- Добавить transactional outbox, чтобы надежно связывать изменения PostgreSQL с публикацией в Kafka.
- Проработать обработку временных ошибок, повторы и dead-letter topic, версионирование событий и сценарии replay.
- Добавить меню и frontend; собственный мини-фреймворк на Custom Elements пока отложен.
- После основного сценария определить объем доставки, уведомлений, учета, способы оплаты, отмены и возвратов.

Для локального учебного кластера используется один Kafka broker с replication factor 1; это не обеспечивает отказоустойчивость production-кластера.

## 9. Вопросы для уточнения
Нужно решить, какие способы оплаты поддерживаются и как обрабатываются отмена и возврат.
Также предстоит определить, какие каналы заказа и способы получения
войдут в первую версию и нужны ли доставка и учет. Начальная реализация выбрана
как модули одного приложения; разделение на отдельные сервисы можно пересмотреть позже.
